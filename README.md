# GCP MLOps Capstone: income prediction, end to end

This is a production-style MLOps system on Google Cloud. It predicts whether a person is in the high-income segment, using the public US census dataset in BigQuery.

The system needs to:
- **Ship automatically:** every push to `main` is tested, built and deployed.
- **Retrain nightly:** the model retrains every night through a reproducible pipeline.
- **Gate on quality:** a quality gate blocks any model below ROC AUC 0.90.
- **Explain predictions:** each prediction comes with feature attributions, plus a plain-language summary generated by Gemini.
- **Watch for drift:** input drift triggers an alert.

> Status: **Stage 4 of 5, live on GCP.** A Vertex AI pipeline retrains every night, validates, gates, registers and redeploys the model. Every prediction can be explained with exact Shapley attributions and a plain-language summary from Gemini. Terraform foundations, the BigQuery training table, a first model (test ROC AUC **0.9196**, which passes the 0.90 gate) and the Cloud Build → Cloud Run deployment are working. A full build (tests → image → deploy) takes about 3.5 minutes. The Vertex AI pipeline, the nightly schedule, explanations and monitoring come next (see the roadmap below).

## Architecture

```text
GitHub ──push──▶ Cloud Build: lint + tests ─▶ docker build ─▶ Artifact Registry ─▶ Cloud Run (scale to zero)
                                (gate)                                                 │ loads model from GCS
BigQuery (public census) ─▶ mlops.income_training (hash split 80/10/10)               ▼
        └──▶ Vertex AI Pipeline: extract → validate → train → evaluate ─AUC ≥ 0.90?─▶ GCS models/current + Model Registry
                 ▲ nightly schedule 03:00                                                  │
                 └──────────── Model Monitoring: drift alert → email / retrain trigger ◀───┘
```

## Run locally (no GCP account needed)

```bash
make install
make test          # 31 tests: reproducibility, quality gate, API contract
make docker-build
```

## Deploy to GCP

```bash
# 0. One-time bootstrap: APIs Terraform needs before it can read the project
gcloud services enable cloudresourcemanager.googleapis.com serviceusage.googleapis.com \
  iam.googleapis.com cloudbilling.googleapis.com

# 1. Infrastructure
cd infra/terraform
cp example.tfvars terraform.tfvars   # fill in project_id and billing_account
terraform init && terraform apply

# 2. Data (stage 1)
bq query --use_legacy_sql=false < sql/01_prepare_data.sql
PROJECT_ID=<id> .venv/bin/python scripts/validate_split.py

# 3. First model
make train PROJECT_ID=<id>
gcloud storage cp artifacts/model.joblib gs://<id>-mlops/models/current/model.joblib

# 4. Training pipeline (after the first Cloud Build has pushed the trainer image)
.venv/bin/python -m pipeline.run                 # normal run: gate 0.90
.venv/bin/python -m pipeline.run --min-auc 0.99  # gate test: register/deploy must be skipped

# 5. Nightly retraining at 03:00 Europe/Istanbul (re-run after DAG changes; --pause / --resume)
.venv/bin/python -m pipeline.schedule

# 6. CI/CD: connect the GitHub repo in Cloud Build, then create a trigger on main
#    that uses cloudbuild.yaml and the cloud-build-deployer service account.
```

## Design decisions

- **Cloud Run rather than a Vertex AI endpoint for serving.** A Vertex endpoint keeps at least one node running 24/7. Cloud Run scales to zero, which suits sporadic internal traffic and meets G5. The trade-off is a cold start on the first request.
- **Hash-based split, not random.** `FARM_FINGERPRINT` puts the same row in the same split on every run. This keeps metrics comparable and prevents test-set leakage across retrains.
- **Two layers of quality gate.** In the pipeline, register/deploy sits inside a `dsl.If` branch, so a weak model stays a pipeline artifact and is never versioned, registered or served. The standalone `training.train` CLI enforces the same threshold by refusing to write the model.
- **Promotion means a new Cloud Run revision.** The API caches the model in memory. The pipeline changes `MODEL_VERSION` on the service, which creates a new revision that loads `models/current`, and every model also stays in a per-run folder so it can be rolled back.
- **Least privilege.** The API identity can only read model objects. The CI identity can deploy, but it is not Owner or Editor. No service account key files are used anywhere.
- **US BigQuery location.** The public source table is in the US multi-region, and BigQuery cannot query across locations.
- **Same preprocessing in training and serving.** BigQuery returns nullable `Int64` columns while the API builds plain Python types. The first deployment failed on exactly this mismatch, so `training.features.prepare()` now normalises dtypes on both sides, and a regression test trains on BigQuery-style dtypes.
- **`/health`, not `/healthz`.** Cloud Run's frontend reserves paths ending in `z` and returns its own 404.
- **Permutation Shapley values, not TreeSHAP.** TreeSHAP does not handle the model's native categorical splits exactly: base value plus contributions missed the model output by about 2.2 log-odds. The permutation explainer adds up exactly by construction (tested). The cost is about 0.05 s per request after a one-time JIT warm-up. Permutations are re-seeded per call under a lock, so the same input always gets the same explanation.
- **The numbers are the source of truth, and the LLM is best-effort.** If Gemini fails, the endpoint still returns the probability and attributions, with `narrative_error` set. Confidence bands come from the probability in code, not from the LLM.
- **LLM guardrails.** The structured JSON schema keeps the output machine-readable. The prompt forbids causal claims ("the model weighed X", never "X raises income"). One answer out of a dozen came back with stray characters, so output outside the expected character set is retried once with thinking enabled.
- **Known trade-off: cold start.** The first explained request on a fresh instance takes about 20 s (model download, explainer JIT and Gemini client set-up). Warm requests take about 2.5 s, most of it the LLM call. `min-instances=1` would remove the cold start but costs money 24/7, which this demo doesn't justify.
- **Gemini 2.5 Flash (GA, regional) by default.** Gemini 3 Flash was only available as a preview on the global endpoint, and was slower on its first call. The model and location can be changed with `GEMINI_MODEL` and `GEMINI_LOCATION`.
- **Model choice.** `HistGradientBoostingClassifier` handles categorical features natively and is a strong baseline for tabular data. Unseen categories at inference map to "unknown" instead of failing (this is tested).

## Cost and cleanup

Expected cost is a few dollars, well inside the free trial credit. The nightly pipeline costs about $0.10 per run; pause it with `python -m pipeline.schedule --pause` when you aren't using it. After each session:

```bash
gcloud run services delete income-api --region=us-central1   # deployed by Cloud Build, not Terraform
cd infra/terraform && terraform destroy
```

The code and README stay public. The whole system can be rebuilt from scratch with the steps above.
